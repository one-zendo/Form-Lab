## Independent layout architecture
These rules apply to the four diagnostic pages now and to each future product screen independently (Home, Workouts, Progress, Profile, Routine and Active Workout).
- Each screen owns five orientation layouts (FP, FL1, FL2, UP, UL), each sharing its arrangement between Native and Safari, with environment-specific viewport and safe-area calibration.
- One shared UI and component model across orientations and environments. Changes to a component's content, color, typography, icons, visual styling and functionality propagate to every instance of that component. Headline and pop-outs are shared components across screens. Card internal padding is shared component styling. Screen-specific content is shared across that screen's orientations and environments, not automatically added to other screens. Hardware/viewport detection, raw posture signals, diagnostics and application data may be shared without imposing layout decisions.
- Remove all global automatic layout adaptation: no global card grid, sizing, stretching, column switching, spacing, scrolling, navigation placement or hinge-driven composition switching; global arrangement-preserving posture adjustment is approved. No cross-screen card arrangement inheritance, generic portrait/landscape composition, or corrective CSS overrides. Shared orientation alignment is explicitly allowed.
- Each screen/orientation owns card arrangement, dimensions, inter-card gaps, scrolling and hinge response. Changes to these propagate to Native and Safari of that screen and orientation, adapting dimensions to the actual drawable viewport without changing composition or affecting other screens or orientations.
- Each orientation shares outer content margins, headline alignment and main navigation placement across screens, with environment-specific safe areas, calibration and approved navigation positions. Changes to these shared alignment settings affect all applicable screens of that orientation. No global card stretching or automatic column switching.
- Initial normal-state wireframes use two stacked full-width test cards in all five orientations. Card heights and final spacing are provisional; do not force equal-height stretching globally. The future Home UP stays stacked regardless of hinge signal. All five diagnostic orientations include a stacked pair and a side-by-side pair. Semi-folded posture adjusts each along its existing arrangement axis. No posture-driven direction switching.
- Retain raw hinge and viewport segment detection. Maintain current posture as shared state. Only the visible screen needs to render its posture response; on navigation, the destination reads the latest shared posture before its initial layout, without requiring background rearrangement or a transient flat layout. Navigation remains anchored unless an explicitly approved orientation-specific response changes it. Diagnostics distinguish detected posture from actual rendered composition. Never fabricate hinge angle or exact boundary.

## Arrangement-preserving hinge adjustment (approved)
Hinge response adjusts dimensions, spacing and positions, never the existing arrangement direction or card order. Stacked cards remain stacked; side-by-side cards remain side-by-side. Global capability: all screens and orientations participate in posture adjustment, using their existing local arrangement direction. All five current diagnostic layouts separate stacked test cards into upper and lower content areas and side-by-side cards into left and right content areas when semi-folded. Preserve padding and readable content; use minimum card sizes and scrolling instead of excessive shrinking. Restore normal dimensions and gaps on unfolding. Smooth transitions respond to available posture events; continuous angle animation requires verified angle data. Diagnostic sizing targets (96px normal stacked minimum, 68px adjusted minimum, 120px side width where space permits, 24px adjusted gap) are provisional CSS design values, not hardware calibration. These content divisions are UI design boundaries, not physical hinge claims. Navigation and timer remain anchored and state is preserved. Use actual reported segment boundaries when compatible with the approved content axis; otherwise the diagnostic layouts use a provisional midpoint of the drawable viewport as a design reference, not a sensor measurement. Unknown posture does not trigger adjustment. Provide a clearly labeled diagnostic simulation for testing when posture APIs are unavailable. Motion respects reduced motion. Physical calibration remains pending.

## Viewport and calibration
Use actual drawable viewport; never subtract Safari exclusions twice. Keep system safe insets distinct from design margins. Match reference viewport within 2 CSS px; folded landscape angle 90 = FL1, 270 = FL2, otherwise ambiguous. Unknown stays unknown. Preserve the approved FL1 Safari zero left design margin while retaining system inset; Native FL1 reference margin 16px. Apply these as shared orientation/environment alignment settings, not global screen composition. Camera avoidance is local; previous 4px clearance is provisional. CSS px are not guaranteed physical pt.

## Diagnostic app zoom policy (approved)
The diagnostic app uses a fixed-scale interface. Prevent accidental pinch and double-tap page zoom where supported, and avoid input-focus zoom using appropriately sized editable text. Preserve normal scrolling, rotation, hinge detection and system accessibility zoom. Browser-enforced zoom behavior may not be suppressible; verify on physical Duo Safari rather than claiming universal prevention.

## Navigation and motion
Diagnostic navigation destinations: Home, Workouts, Profile, Diagnostic. Home contains card pairs; Workouts contains exercise tests; Profile contains sample controls; Diagnostic contains global posture simulation, master guides and individual viewport, headline, card/control, camera, hinge/division and safe-area toggles, plus measurements. Keep timer anchored across all pages for testing. Settings and interaction state persist across page navigation and rotation during the session. Hidden pages do not contribute overlay geometry. Future product navigation is separate. Preserve selected destination across rotation. Navigation state and appearance are shared. Dock geometry and placement are shared across main screens per orientation and environment. Approved positions: FP Native right, FP Safari bottom; FL1 and FL2 right in both environments; UP and UL bottom in both environments. Navigation visibility belongs to each screen. Secondary screens may hide the main dock and use their own back or task controls while retaining shared orientation margins and headline alignment; exact controls require screen-specific design. Prior 80px rail, 332px maximum bottom dock and 44px minimum controls are reference values, not global layout rules. Keep navigation anchored while content scrolls. Motion is local, transform-only where appropriate, respects reduced motion and avoids crossing reported segment boundaries. No global motion-driven layout changes.

## Rest timer placement (approved)
Use a floating rest timer anchored independently of scrolling content and navigation. FP, FL1 and FL2 place it at the bottom center of the content area; UP and UL center it above the bottom dock. FP Safari also places it above the bottom dock. Each orientation owns its timer placement, adapting to Native/Safari drawable areas and avoiding camera and unavailable regions. Reserve sufficient scroll clearance for both anchored controls. Preserve timer state across rotation and posture changes. Share timer appearance and interaction across orientations; exact dimensions and offsets remain provisional pending physical validation.

## Visual direction (approved)
Combine Apple-inspired calm minimalism, glass-inspired navigation and floating controls, refined typography and restrained spring motion with ChatGPT-inspired intelligent UI: contextual interactive components, progressive disclosure, expandable details, meaningful visualizations and concise conversational insights. Prefer solid readable content cards, purposeful accents, clear hierarchy and light/dark appearance with accessible contrast. Lucide is the standard icon library; use consistent stroke weights and recognizable symbols, avoiding decorative clutter. Preserve approved radius tokens and layout ownership. Intelligent presentation does not authorize global spatial rearrangement or unapproved AI functionality. Production insights and workout features require later implementation and validation.

## Shared corner radius tokens (approved)
All screens, orientations and environments use the same component radius tokens. Cards: 16 pt; buttons: 12 pt; small controls: 8 pt; pop-outs: 24 pt; navigation dock: 28 pt; capsules: fully rounded (half the shorter dimension). Define each token once; changing it updates every component using it without changing spatial arrangement. Component colors and other visual tokens likewise propagate to all instances; changing a particular card's color does not recolor unrelated cards unless they share that token. Hardware corner radii remain separate and untouched. Web CSS values are logical design units, not verified physical measurements.

## Replace, never override
Permanent layout changes replace the existing local placement definition. Delete superseded declarations, conditions, fallback arrangements and corrective overrides for that placement; do not layer new rules over obsolete ones. Maintain one authoritative definition per ownership scope: shared orientation/environment alignment and navigation, and screen/orientation card arrangement with explicitly approved posture states. Permanent arrangement direction must not be overridden by hinge signals; approved posture adjustment may change dimensions and spacing. Preserve shared UI components, functionality, hardware detection, diagnostics and user data. Retain previous implementations only in Git history. Verify no conflicting active definitions remain.

## Engineering principles and layer boundaries
No hidden automation: rearrangement, stretching and movement require an explicit local design. Remove unused styles, variables, functions and obsolete conditions as part of every change. Rotation and posture changes must preserve selected screen, workout state and user input.
Separate five responsibilities:
- Hardware: report orientation, drawable viewport, safe areas and raw hinge/posture signals; never dictate card placement.
- Layout: own shared orientation alignment and navigation, plus independent screen/orientation content arrangements with local Native/Safari viewport adaptation.
- Components: share appearance, content, typography, colors, icons and controls across orientations; no global spatial adaptation.
- Functionality: share interactions, application logic and persistent data independently of layout.
- Diagnostics: observe and report actual geometry and signals; overlays must never alter layout, dimensions, scrolling or interaction.
## Automatic build updates (approved)
Check the deployed version manifest every 3 seconds while visible, and on return to foreground. Reload only for a newer matching-series build after verifying the deployed HTML build marker. Bypass caches and version runtime asset URLs. Defer reload during editing, changed input, active or modified timer, completed set, nondefault navigation, tap tests or open dialog. Show pending version; never clear user storage. Browser background throttling and deployment latency mean three seconds is a polling target, not a delivery guarantee.

## Development discipline
Preview and approve spatial arrangements before implementation. Establish and physically test the minimal wireframe before adding workout features. Follow the verification section; automated browser checks do not substitute for physical Duo or native validation. Remove superseded code in every build; verify that no conflicting definitions remain. Record approved decisions and known limitations, preserve data and Git history, work directly on main, and verify deployment separately from source changes.
